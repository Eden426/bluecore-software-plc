# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

This is an npm-workspaces monorepo. Run `npm install` once at the repo root; the single `package-lock.json` lives there.

- `apps/web` (`@bluecore/web`): the marketing site. **Everything in "Project overview", "Commands" and "Architecture" below describes this app, and file paths there (`src/...`, `scripts/...`, `api/...`, `vercel.json`, `docs/...`) are relative to `apps/web/`.**
- `apps/support` (`@bluecore/support`): the support center and staff admin console (Vite + React 19 + Tailwind v4 + `react-router`, backed by Supabase). The public side (`src/pages/help/`) is the help center: home with search, `/kb`, `/faq`, `/docs` and `/docs/:productSlug`, `/updates`, `/articles/:slug` and `/search`. It reads published public `kb_articles` as `anon`. Markdown goes through `src/components/Markdown.jsx` (react-markdown, which doesn't render raw HTML). `VITE_SUPPORT_EMAIL` sets the contact address shown and defaults to `team@blue-core.tech`. `/admin/*` is staff-only and covers:
  - help center content: a CMS for articles, FAQs, docs and updates, with draft/published/archived status, public/internal visibility, a markdown preview and helpful-vote totals
  - tickets: a queue with My/Unassigned/All/Done views and SLA badges, plus a detail page with the threaded conversation, replies, internal notes, a triage panel and the audit trail
  - clients: email domains, contacts and deployments
  - products: shared vs bespoke
  - staff roles

  Server functions live in `api/` (Vercel-style `export default { fetch }`), with pure helpers in `server/`:
  - `api/inbound-email.js` is the Resend `email.received` webhook.
  - `api/tickets/reply.js` sends agent replies by email.

  `npm run dev` serves `api/` through a Vite dev middleware (`vite.config.js`), and `SUPPORT_EMAIL_TRANSPORT=log` logs replies instead of emailing. See `apps/support/docs/email-setup.md`. Data access goes through `src/lib/api.js`. `src/lib/permissions.js` only hides controls; **the real gate is RLS** in `supabase/migrations`. The auth context, provider and hook are split across `src/auth/` (same Fast Refresh reason as `apps/web`'s theme files). Env: `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` (see `apps/support/.env.example`). Later phases: ticketing with AI triage, Resend inbound email, the help center CMS, live chat, and Google Calendar booking. It doesn't deploy anywhere yet.
- `supabase/`: the Supabase project for `apps/support`, covering migrations, `seed.sql` (local only), pgTAP tests in `tests/`, and `config.toml`. Access model:
  - Only Bluecore staff authenticate. Self-signup is off via `[auth] enable_signup = false`. Keep `[auth.email] enable_signup = true`, because setting it false disables password login entirely.
  - Admins create users in the Supabase dashboard. A trigger gives each new auth user a `staff` row with the `viewer` role.
  - Roles: `viewer` reads, `agent` also manages contacts, `admin` manages everything including roles. A trigger keeps at least one active admin. The first admin must be promoted with SQL (`update staff set role = 'admin' ...`).
  - New tables need explicit `grant`s to `authenticated` **and** `service_role`, because newer Supabase doesn't auto-grant (see `20261022130100_service_role_grants.sql`).
  - Help center: `kb_articles` are readable by `anon` only when published and public. `search_kb()` is public-only by default even for staff, and staff tools pass `include_internal => true`. Anyone can insert a `kb_feedback` vote, but only staff can read votes. `anon` can read only shared, active products (and only the columns `id, name, slug, description, kind, active`), because bespoke product names identify clients.
  - Customer and system messages are only written server-side, through `ingest_inbound_email()` (service role only) or `create_staff_ticket()` (agent-checked). RLS lets agents insert only `agent`/`note` messages as themselves.
  - Local ports are moved to the 571xx range so they don't collide with other local Supabase projects on this machine.
  - Local workflow:
    - Start: `supabase start -x analytics,vector,studio,imgproxy,edge-runtime,storage-api,realtime,postgres-meta,logflare,supavisor`
    - Reset: `supabase db reset` (it re-applies the migrations and seed, and sometimes hangs on its container restart after it has already finished)
    - Test: `supabase test db`
    - Seed logins are listed at the top of `seed.sql`.
  - CI runs `supabase test db` in the `database` job, and `deploy` also waits on it.
- `packages/brand` (`@bluecore/brand`): shared brand tokens (`tokens.css`). `apps/support` imports it. `apps/web` still defines its own copy in `src/index.css`, so change brand colors in both places.

Root scripts fan out to every workspace (`npm run build|lint|test` runs `--workspaces --if-present`). `npm run dev` starts the marketing site, and `npm run dev:support` starts the support app. To target one workspace, use `npm run <script> -w @bluecore/web`.

## Project overview

A marketing website for Bluecore Software PLC, built with React 19 + Vite + Tailwind CSS v4, live at blue-core.tech. There is no router library — `App.jsx` reads `window.location.pathname` directly (via `resolveRoute()`) and renders one of: the home page (a stack of `<section>` components linked by in-page anchors: `#home`, `#about`, `#services`, `#portfolio`, `#team`, `#contact`), a legal/support page (`/privacy`, `/terms`, `/support`, rendered by `LegalPage`), a service detail page (`/services/:slug`, looked up in `src/data/services.js`), a portfolio detail page (`/portfolio/:slug`, looked up in `src/data/portfolio.js`), the blog index (`/blog`) or a blog post (`/blog/:slug`, looked up in `src/data/blog.js`), or `NotFoundPage` for anything else/unmatched slug.

## Commands

Run these from the repo root (they target `apps/web`, except `build`/`lint`/`test`, which cover all workspaces), or from `apps/web` itself.

```bash
npm run dev       # start Vite dev server
npm run build      # generates public/sitemap.xml, builds to dist/, then prerenders every route (see below)
npm run preview    # preview the production build
npm run lint       # eslint over the whole repo
npm test           # run the vitest suite (jsdom + Testing Library)
```

Test files live in `src/test/` (e.g. `theme-navigation.test.jsx`, `contact-chat.test.jsx`). Run a single file with `npx vitest run src/test/theme-navigation.test.jsx`, or `npx vitest` for watch mode.

`npm run build` is `node scripts/generate-sitemap.mjs && vite build && node scripts/prerender.mjs`.

`scripts/generate-sitemap.mjs` writes `public/sitemap.xml` from the same plain data files that drive the site's routes (`src/data/services.js`, `portfolio.js`, `blog.js`), stamping every URL with the current date as `lastmod`, before Vite runs — so Vite copies the regenerated file into `dist/` like any other static asset, and the sitemap can't drift out of sync with what routes actually exist the way a hand-maintained one did previously.

`scripts/prerender.mjs` spins up a static server over `dist/`, then for every route in its `ROUTES` list loads it in headless Chrome and writes the fully rendered DOM (`document.documentElement.outerHTML`) to `dist/index.html` (for `/`) or `dist/<route>/index.html` (everything else). This exists because the app is client-rendered only (`main.jsx` uses `createRoot`, not `hydrateRoot`/SSR), so the raw `vite build` output ships an empty `<div id="root">` — fine for browsers and JS-executing crawlers (Googlebot), but most AI crawlers (GPTBot, ClaudeBot, PerplexityBot, CCBot) fetch HTML without running JS and would otherwise see none of the page copy. Because `main.jsx` still calls `createRoot(...).render()` on load, real users' browsers discard the prerendered DOM and re-render client-side as normal — the prerendered HTML only matters for the first non-JS fetch.

**`ROUTES` covers every static route plus every service/portfolio/blog slug**, derived by importing `services.js`, `portfolio.js`, and `blog.js` directly (all three are plain data with no JSX or asset imports, specifically so a plain Node script can import them — see the "Icons" bullet below). `team.js` is *not* imported here: it pulls in `.webp`/`.svg` asset imports a plain Node script can't resolve, and team members don't have their own routes, so it isn't needed. If you add a new top-level route or a new detail-page kind (not just a new entry in an existing data file — those are already covered automatically), add it to `ROUTES` in `scripts/prerender.mjs` and to the URL list in `scripts/generate-sitemap.mjs`.

`ROUTES` is exhaustive (every route `resolveRoute` in `App.jsx` can match has its own prerendered `dist/<route>/index.html`), so there's no SPA-fallback rewrite in `vercel.json` — Vercel's filesystem routing serves each prerendered file directly. `scripts/prerender.mjs` also renders `dist/404.html` (from a sentinel path that doesn't match any real route, so it falls through to `App.jsx`'s `NotFoundPage` branch), which Vercel serves natively, **with a real 404 status**, for any request that doesn't match a route — this matters for SEO: before this existed, an unmatched/mistyped URL fell through to `dist/index.html` and was served as a 200, which search engines interpret as a duplicate of the homepage. Don't rely on `vite preview` to validate any of this: it doesn't apply `vercel.json` or Vercel's static-file/404 routing, so it serves every path through `dist/index.html` regardless of whether a matching `dist/<route>/index.html` or `dist/404.html` exists.

`scripts/prerender.mjs` launches its browser two different ways depending on environment (see `launchBrowser()`): on CI/Vercel (`process.env.CI` or `process.env.VERCEL` set) it uses `puppeteer-core` + `@sparticuz/chromium`, a Chromium build statically compiled for restricted serverless/CI Linux containers — plain `puppeteer`'s bundled Chromium fails there with missing shared libraries (`libnspr4.so` etc.). Locally it falls back to full `puppeteer`, which downloads a Chromium that runs on the host OS (`@sparticuz/chromium`'s binary is Linux-only and can't launch on macOS). Both packages are devDependencies for this reason — don't remove either without checking which environments still need it.

### Deployment

`.github/workflows/deploy.yml` runs on every push and PR to `main` with two jobs:
- `validate` (runs on PRs and pushes): `npm ci`, `npm run lint`, `npm test`, `npm run build` (all workspaces). On same-repo PRs it also runs `vercel pull` + `vercel build --prod` from `apps/web` (no deploy), so a broken deploy path fails the PR instead of the push to `main`.
- `deploy` (runs only on push to `main`, after `validate` passes; every step runs with `working-directory: apps/web` — the Vercel project's Root Directory setting is deliberately left unset, so don't set it in the dashboard, or the CLI would look for `apps/web/apps/web`): `vercel pull` → `vercel build --prod` → `vercel deploy --prebuilt --prod`, i.e. the build (including the prerender step, using the CI/`@sparticuz` path above) happens in the Actions runner, not in Vercel's own build container — Vercel's native build container has the same missing-shared-library problem plain `puppeteer` had, and using `--prebuilt` sidesteps it entirely regardless of which Chromium strategy is in play.

The workflow needs `VERCEL_TOKEN`, `VERCEL_ORG_ID`, and `VERCEL_PROJECT_ID` configured as repo secrets (values in `.vercel/project.json` for the latter two once linked). Vercel's native GitHub integration (auto-build-on-push via Vercel's own container) is intentionally not used here.

For manual/local deploys, run from `apps/web` (link it with `vercel link` there): `vercel build --prod` then `vercel deploy --prebuilt --prod` (same reasoning — avoids Vercel's build container running Puppeteer).

## Architecture

- **Composition root / routing**: `src/main.jsx` wraps `App` in `ThemeProvider`. `src/App.jsx` does its own pathname-based branching (no router library): `resolveRoute(path)` matches static routes (`/`, `/privacy`, `/terms`, `/support`, `/blog`) against the hand-maintained `routeMetadata` map, and matches `/services/:slug`, `/portfolio/:slug`, `/blog/:slug` by looking up the slug in `src/data/services.js`, `portfolio.js`, `blog.js` respectively — an unmatched slug falls through to `NotFoundPage` like any other unrecognized path. `App` then renders the home page's section stack in order (`Navbar`, `Hero`, `AboutPreview`, `Stats`, `Services`, `Team`, `Portfolio`, `Testimonials`, `Contact`, `Footer`, plus `SupportChat`/`Analytics`/`SpeedInsights` outside the switch) for `route.view === "home"`, or the matching detail/index component otherwise. `App.jsx` also hand-rolls per-route `<title>`/meta-description/canonical/OG/Twitter tag updates (`useRouteMetadata`, driven by `route.metadata` — static for the hand-maintained routes, computed from the matched data-file entry for detail pages) and a hash-scroll effect (`useHashScroll`) that re-implements the browser's native fragment-scroll behavior, which client-side rendering destroys (see the comments above those functions in `App.jsx` for why). To reorder or add a home-page section, edit the JSX inside the `route.view === "home"` branch; to add a new *top-level* route (not a new service/portfolio/blog entry — those become routes automatically via `resolveRoute`), add it to `routeMetadata`, branch on it in `resolveRoute`, and extend `scripts/prerender.mjs`'s `ROUTES` and `scripts/generate-sitemap.mjs`'s URL list — there's no route config file that covers all three at once.
- **Theming**: dark mode is a `.dark` class on `<html>`, toggled via `src/context/ThemeProvider.jsx` and read anywhere with the `useTheme()` hook (`src/context/useTheme.js`). Dark is the default for first-time visitors (no saved preference); the choice persists to `localStorage` under `THEME_STORAGE_KEY` from `src/constants/theme.js`. The context object/provider/hook are split into three files (`themeContext.js`, `ThemeProvider.jsx`, `useTheme.js`) — this split exists because Vite's React Fast Refresh requires files that export components to only export components, so the raw context and the hook live outside `ThemeProvider.jsx`.
- **Tailwind v4 setup**: Tailwind is imported via `@import "tailwindcss";` directly in `src/index.css`, not configured through `tailwind.config.js`'s `theme` block (that file mainly declares `content` globs). Dark-mode variants use a custom variant `@custom-variant dark (&:where(.dark, .dark *));` also defined in `index.css`, so `dark:` utility classes key off the `.dark` class rather than `prefers-color-scheme`. Brand colors are CSS custom properties on `:root` in `index.css` (`--bluecore-blue`, `--bluecore-primary`, `--bluecore-accent-blue`, `--bluecore-brown`, `--bluecore-accent-brown`, `--bluecore-text`, `--bluecore-border`, etc.) alongside hardcoded hex values used directly in component `className` strings (e.g. `#06243f`, `#8B5E3C`, `#09090B`) — when changing brand colors, check both places.
- **Content/presentation split**: copy and structured content for repeatable sections lives in `src/data/` (`portfolio.js`, `services.js`, `team.js`, `blog.js`) rather than inline in JSX, so editing the portfolio list, service catalog, team roster, or blog posts means editing data files, not component markup. `services.js` entries can carry an optional `hero: true` flag plus `heroTagline`/`heroExtended` fields that `Services.jsx` uses to render one featured/expanded card differently from the rest. `services.js` and `portfolio.js` also carry a stable `slug` (used for that entry's `/services/:slug` or `/portfolio/:slug` route — see the routing bullet above) plus `overview`/`included` or `overview`/`highlights` fields used only by the detail page, not the homepage card. **`services.js`, `portfolio.js`, and `blog.js` are deliberately plain data with no imports of JSX or bundler-only assets** (icons, `.webp`/`.svg`) — `scripts/prerender.mjs` and `scripts/generate-sitemap.mjs` import them directly from plain Node, which can't parse JSX or resolve asset imports the way Vite can. Keep it that way: if a new field needs a component or asset (an icon, an image), map it separately by `slug`/`type` in its own file instead of putting it in the data file (see the "Icons" bullet, and `src/data/portfolioImages.js`'s map keyed by `type` — a sibling of `portfolio.js` rather than a `Portfolio.jsx` export, since a file exporting a component can't also export a plain constant without breaking Fast Refresh).
- **Icons**: `src/components/icons/ServiceIcons.jsx` exports custom inline SVG icon components (`IconAI`, `IconCloudOps`, `IconIntegration`, etc.) used by `Hero.jsx`'s badge row. `src/data/serviceIcons.js` maps each service's icon component by `slug` (`serviceIcons[service.slug]`) — this indirection (rather than an `icon` field directly on the `services.js` objects) is what keeps `services.js` JSX-free per the bullet above; `BentoServiceCard.jsx` and `ServiceDetail.jsx` both look the icon up this way. General-purpose UI icons (menu, sun/moon, contact icons) come from `lucide-react` instead.
- **Structured data (JSON-LD)**: `src/lib/structuredData.js` builds schema.org objects (`Organization`, `WebSite`, `Service`, `CreativeWork` for portfolio projects, `BlogPosting`, `BreadcrumbList`) from the same data files, rendered into the page via `<JsonLd>` (`src/components/JsonLd.jsx`). The site-wide `Organization`/`WebSite`/full `Service` and project catalog is rendered once in `App.jsx` outside the route switch, so it's present on every page; each detail page additionally renders its own specific schema plus a `BreadcrumbList`. There's no static JSON-LD in `index.html` — it was removed in favor of this generated version specifically to avoid two copies drifting apart.
- **Contact API**: `api/contact.js` is a Node.js Vercel Function using the Web Request/Response handler. The form posts same-origin JSON and the function calls Resend over HTTPS with server-only configuration. Shared validation is in `src/lib/contactValidation.js`. `SupportChat` remains local quick-help with ordinary contact links. See `docs/contact-setup.md` for environment variables, required Vercel WAF rate limiting, local `vercel dev`, and deployment steps. `npm run dev` and `npm run preview` serve the frontend only.
